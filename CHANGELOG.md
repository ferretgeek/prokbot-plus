## ProkBot Plus 1.16.1 (2026-11-26)

桌面客户端（官方 1.3.0）的三处修补，由 jun9100 贡献（#21、#23）。用新的 Windows、Mac 或 Linux 包重新生成客户端后生效；用 1.1.0 界面的 Android 和网页版也有一处相同的修补，重新生成后生效。Host 和 iOS 不变。Three fixes for the desktop clients on the official 1.3.0, contributed by jun9100 (#21, #23). Rebuild the client with the new Windows, Mac or Linux package to get them; Android and the web client on the 1.1.0 interface get one of the same fixes after a rebuild. The Host and iOS are unchanged.

- **连接应用 / Connected apps**：Mac 上「这台 Mac」分组里的备注、提醒事项、日历、地点、通讯录，以及各平台的本地 Obsidian 条目一直在转圈，后台还每 5 秒重试一次。Host 用不上这些本机工具，现在不再显示，对应的读取按官方「不可用」的值返回；Host 提供的应用不受影响。Android 和网页版的 1.1.0 界面也会调用这些读取，同样补上了。The Notes, Reminders, Calendar, Location and Contacts entries under "This Mac" (on the Mac) and the local Obsidian entry (on every platform) kept spinning and retried every 5 seconds in the background. The Host cannot serve these local tools, so they are no longer shown and their reads return the official "unavailable" values; Host-served apps are unaffected. The 1.1.0 interface used by Android and the web client calls the same reads and now gets the same answers.
- **自动化详情 / Automation details**：打开自动化详情、读取团队成员或邮件邀请资格时不再报「未实现」，按官方离线时的空值返回。Opening automation details, or reading team members or email invitation eligibility, no longer fails with "not implemented"; these reads return the official offline empty values.
- **Mac arm64 签名 / Mac arm64 signing**：生成 Apple 芯片客户端时按 16 KiB 页签名，与官方 1.3.0 一致。之前在 Intel Mac 上交叉生成会按 4 KiB 页签名，Apple 芯片同样能运行。The Apple Silicon client is now signed with 16 KiB pages like the official 1.3.0. Cross-builds on Intel Macs previously used 4 KiB pages, which Apple Silicon also accepts.

## ProkBot Plus 1.15.1 (2026-11-25)

修复 1.15.0 的一个问题：同机部署开启只读记忆挂载后，给 Bot 发带附件的消息，这一轮会失败（`EROFS: read-only file system`），Bot 收不到附件。Host 原来每轮都把附件再写一份到 Bot 的电脑上，而这个目录在 1.15.0 起是只读挂载；现在 Bot 的电脑已经能通过只读挂载读到附件时就不再复制，分开部署和没有开启挂载时照旧复制。**已升级到 1.15.0 的 Host 请再执行一次 `python3 deploy.py update < /dev/null`**；客户端不用重新生成。Fixes a 1.15.0 problem: on same-machine deployments with the read-only memory mounts, a message with attachments failed for that turn (`EROFS: read-only file system`) and the Bot did not receive the attachments. The Host copied each attachment to the Bot's computer on every turn, into a directory that 1.15.0 mounts read-only; it now skips the copy when the Bot's computer already reads the attachment through the read-only mount, and still copies it for separate execution nodes and deployments without the mounts. **Hosts already on 1.15.0 should run `python3 deploy.py update < /dev/null` again**; clients need no rebuild.

## ProkBot Plus 1.15.0 (2026-11-25)

安全修复，移植自上游 ProkBot v2026.11.25。**所有 Host 都建议尽快升级**（`python3 deploy.py update`）；客户端不用重新生成，已上传的网页版界面包继续可用。用 HTTPS 反向代理访问网页版的，升级前先看下面「反向代理」一条。A security release ported from upstream ProkBot v2026.11.25. **Every Host should upgrade soon** (`python3 deploy.py update`); clients need no rebuild, and the uploaded web client bundle keeps working. If browsers reach the web client through an HTTPS reverse proxy, read "Reverse proxy" below before upgrading.

- **网页版换到单独的端口和网址 / The web client moves to its own port and address**（影响 1.5.0–1.14.0 / affects 1.5.0–1.14.0）：网页版原来和管理页在同一个网址下，界面包里的官方界面代码（或界面里的 XSS）能借用同一浏览器里管理员的登录状态调用管理接口，例如把模型地址改到别处、套走保存的 API Key。现在网页版由 Host 的第二个端口提供（容器内 8001，Compose 默认映射到 18081，`GROKBOT_WEB_PUBLIC_PORT` 可改），这个端口没有管理接口；管理页的端口不认网页版的 Cookie。「在此浏览器打开」改用一次性、两分钟有效的票据，界面 HTML 禁止被其他页面嵌入。The web client used to share the admin page's address, so the official interface code in the bundle, or an XSS in it, could use the administrator's session in the same browser to call the admin API, for example to point the model address elsewhere and capture the saved API key. The web client is now served on a second Host port (8001 in the container, mapped to 18081 by Compose; change it with `GROKBOT_WEB_PUBLIC_PORT`) that has no admin API, and the admin page's port ignores the web client cookie. "Open in this browser" uses a one-time ticket valid for two minutes, and interface HTML cannot be framed by other pages.
- **升级后的网页版地址 / The web client address after upgrading**：默认是原主机名加 18081 端口，例如 `http://192.0.2.10:18081/web/`；`update`、`doctor` 和管理页「网页版」都会显示。旧的 `<管理页地址>/web/` 自动跳转过去。主机名不变时已登录的浏览器不用重新配对（Cookie 不区分端口）。防火墙或云安全组要放行新端口；同一台机器上的多个实例要在各自 `.env` 写不同的 `GROKBOT_WEB_PUBLIC_PORT`，端口被其他容器或本机其他程序占用时，`update` 在构建前就拒绝，不会停掉旧服务。新装可用 `init --web-port` 和 `--web-public-url`。By default it is the old host name with port 18081, for example `http://192.0.2.10:18081/web/`; `update`, `doctor` and the admin page's Web client section show it. Old `<admin address>/web/` links redirect there. With the same host name, signed-in browsers need not pair again (cookies do not depend on the port). Open the new port in firewalls or cloud security groups; several instances on one machine need different `GROKBOT_WEB_PUBLIC_PORT` values in their `.env`, and `update` refuses a port another container or program already uses before building, without stopping the old services. New installations can use `init --web-port` and `--web-public-url`.
- **反向代理 / Reverse proxy**：网页版要单独一个入口，建议用子域名（例如 `https://web.bot.example.org` 转发到回环 18081，支持 WebSocket），并在实例 `.env` 加 `GROKBOT_WEB_PUBLIC_URL=https://web.bot.example.org` 再 `update`；不能用 `https://bot.example.org/web/` 这样的路径放在管理页网址下，`GROKBOT_WEB_PUBLIC_URL` 和 `GROKBOT_PUBLIC_URL` 相同时 Host 不启动。换成子域名后浏览器要重新配对。nginx 示例见 Host 说明的「网页版」一节。Give the web client an entry of its own, preferably a subdomain (for example `https://web.bot.example.org` forwarding to loopback 18081, with WebSockets), add `GROKBOT_WEB_PUBLIC_URL=https://web.bot.example.org` to the instance `.env` and run `update`. A path under the admin address such as `https://bot.example.org/web/` does not work, and the Host refuses to start when `GROKBOT_WEB_PUBLIC_URL` equals `GROKBOT_PUBLIC_URL`. After moving to a subdomain, browsers pair again. The Host guide's Web client section has an nginx example.
- **记忆目录改为只读 / Memory trees become read-only**（影响 1.7.0–1.14.0 / affects 1.7.0–1.14.0）：同机部署原来把五个记忆目录可写地挂进 Bot 的电脑，Bot 能改写任何 Bot 的记忆、技能和自动任务（包括原版信任的 `"provenance": "user"`）；这些挂载写在默认的 `compose.yaml` 里，不经 `deploy.py` 直接用 Compose 部署、且 Docker Engine 低于 26 时，会把整个 `host-data`（含模型 Key 和登录凭据）挂进去。现在挂载全部只读，放在单独的 `compose.memory.yaml`，只有 `deploy.py` 确认 Docker Engine 26+（API 1.45+）和 Compose 2.26+ 时才加上；版本不够时跳过这一项，部署照常进行，Docker 最低版本要求随之取消。`update` 会把旧的可写挂载换成只读，更新前的检查和 `backup` 接受旧挂载。On same-machine deployments the five memory trees were mounted writable into the Bot's computer, so a Bot could rewrite any Bot's memory, skills and automations, including the `"provenance": "user"` the original trusts. The mounts were in the default `compose.yaml`, so plain Compose deployments without `deploy.py` on Docker Engine before 26 mounted all of `host-data`, model keys and sign-in credentials included. The mounts are now read-only and live in a separate `compose.memory.yaml`, which `deploy.py` adds only after confirming Docker Engine 26+ (API 1.45+) and Compose 2.26+; with older versions it skips this part and deploys anyway, so the minimum Docker versions are gone. `update` replaces the old writable mounts with read-only ones; the checks before an update and `backup` accept the old mounts.
- **备用模型 / Fallback models**：额度耗尽（402 等）后，后面用其他 Key 的备用模型不再被跳过。After a quota failure such as 402, later fallbacks with other keys are no longer skipped.
- **说明 / Notes**：上游同一版本对 Mac Codex 项目检查和 401 原因的客户端修复，以及 Tailcat 的更新，这次没有包含。The upstream client fixes from the same release (the Mac Codex project check and the 401 reason) and its Tailcat update are not included yet.

## ProkBot Plus 1.13.0 (2026-11-25)

模型的上下文长度和思考强度可以自动跟随上游，上下文超限时 Host 会记下真实上限，由 @jun9100 贡献（[#19](https://github.com/ferretgeek/prokbot-plus/pull/19)）。只需升级 Host，客户端都不用重新生成。升级不会改变现有配置：已有的模型档案都保持手动，也不会因此发出后台请求。Model context windows and reasoning efforts can now follow the provider automatically, and the Host learns the real limit when a request overflows, contributed by @jun9100 (#19). Only the Host needs upgrading; no client rebuild is needed. Upgrading keeps existing settings: existing model profiles stay manual and trigger no background requests.

- **自动与手动 / Auto and manual**：每个模型档案的上下文长度和思考强度都可以选「自动」或「手动」。自动档案跟随上游 `/models` 返回的上下文长度（至少 1024）和思考强度档位；路由选的档位上游不支持时，降到最接近的支持档位，不会降成 `none`。手动档案和原来一样。旧档案（包括只用命令行配置过的 Host）和没写模式的配置都按手动处理；内置参考表只在管理页作为建议值显示，确认后才存成手动值。Each model profile can set its context window and reasoning efforts to auto or manual. Auto profiles follow the context window (at least 1024) and effort levels reported by the provider's `/models`; a route effort the provider no longer lists steps down to the nearest supported level, never to `none`. Manual profiles behave as before. Existing profiles, including Hosts configured only from the command line, and configs without a mode are manual; built-in reference values appear only as suggestions in the admin page and are saved as manual values once accepted.
- **超限自愈 / Overflow self-healing**：自动档案遇到 `a + b > c` 这类比较式的超限报错，或连续两次相同的超限报错时，记下真实上限，保留 30 天；自动档案的摘要阈值按扣除输出预留后的 75% 计算（Anthropic 200K 模型为 102K）。手动档案不受影响。管理页能查看和清除记下的上限，手动同步和保存改动过的档案也会清除。For auto profiles, a comparison-style overflow error such as `a + b > c`, or two identical overflow errors in a row, records the real limit for 30 days; their summary threshold is 75% of the window after the output reserve (102K for a 200K Anthropic model). Manual profiles are unaffected. The admin page shows and clears recorded limits, and a manual sync or saving a changed profile clears them too.
- **后台请求 / Background requests**：只有存在自动档案时，Host 才会在启动、保存和每 6 小时带着对应服务的 API Key 请求 `/models`；管理页「上游同步设置」可以关掉。附带 Codex 客户端版本号的探测默认关闭。新增数据文件 `model-context-cache.json`（管理服务写）和 `model-context-observed.json`（运行时写）。Only when an auto profile exists does the Host request `/models` with that provider's API key, at startup, on save and every 6 hours; "Upstream sync settings" on the admin page turns this off. The probe that sends a Codex client version is off by default. New data files: `model-context-cache.json` (written by the admin service) and `model-context-observed.json` (written by the runtime).
- **命令行 / Command line**：`host-admin model-set` 只在带 `--context` 或 `--efforts` 时把档案存成手动，否则沿用原来的模式；`model-catalog` 只采用上游返回的值。`host-admin model-set` saves a profile as manual only with `--context` or `--efforts` and otherwise keeps its mode; `model-catalog` uses only provider-reported values.
- **报错判断（所有用户）/ Error classification (all users)**：更多格式的输入超限报错（Anthropic 的 `a + b > c`、Gemini、中文中转站）会触发压缩；主体是限流的报错（429、TPM、RPM）不再被当成输入超限。带服务商前缀的模型 ID（如 `anthropic/claude-…`）也能匹配参考思考档位。Input-limit errors in more formats (Anthropic `a + b > c`, Gemini, Chinese relays) now trigger compaction, and errors that are about rate limits (429, TPM, RPM) are no longer taken for input limits. Model IDs with a provider prefix such as `anthropic/claude-…` also match the reference effort levels.
- **跟进 / Follow-up**：等前一次同步结束后补跑的同步会先检查开关，关掉自动同步后不再发请求。A follow-up sync that waits for an earlier one now checks the switch first, so turning auto-sync off stops it.

- **记忆挂进 Bot 的电脑 / Memory in the Bot's computer**：同机部署时，Bot 的电脑只挂入 `agents`、`user-memory`、`workflows`、`plugins`、`managed-skills` 五个目录，位置是 `/data/runtime/host-data/<目录>`，和原版 Host 的路径一致，原版的路径保护照样生效（Read 读不了 `store.db`）。`agent-transcripts`、`connector-secrets`、`model.env`、`auth.json`、`projects` 和内部令牌不挂入。部署工具只创建缺失的目录并设置它们的属主，不改已有目录；部署、备份和恢复都核对完整的挂载。On same-machine deployments the Bot's computer gets only these five trees, at the original Host path, so the original path protection still applies (Read refuses `store.db`). Transcripts, connector secrets, `model.env`, `auth.json`, projects and internal tokens stay out. The deployment tool creates only missing directories and sets their ownership; deployment, backup and recovery check the complete mount set.
- **主动用记忆 / Proactive memory**：同机部署时在 Bot 的提示后加一段说明：记忆在哪、需要时主动去读、上一轮读不到要重新检查；加上后超出长度上限就用原提示。`--host-only` 和分开部署的执行电脑不加。The prompt gains a short note on where memory lives, to read it proactively and to recheck earlier failures, falling back to the original prompt if too long. It is not added for `--host-only` or separate execution nodes.
- **Docker 版本要求 / Docker versions**：同机部署需要 Docker Engine 26.0+（API 1.45+）和 Compose 2.26.0+。旧版 Compose 可能忽略子路径、把整个 `host-data` 挂进去，所以 `doctor`、`init`、`up`、`update`、`recover` 在写入或启动前拒绝旧版本。Ubuntu 24.04 系统仓库的 Docker 29.1 和 Compose 2.40 满足要求，`2.40.3+ds1-0ubuntu1~24.04.1` 这类带发行版后缀的版本号能正确识别；`--host-only` 不受限制。Same-machine deployments need Docker Engine 26.0+ (API 1.45+) and Compose 2.26.0+, because older Compose may ignore subpaths and mount all of `host-data`; those commands refuse older versions before writing or starting. Ubuntu 24.04's own packages qualify, distribution suffixes such as `~24.04.1` are parsed, and `--host-only` is not restricted.
- **记录 / Records**：官方 iOS 已到 1.27.0（2026-11-20），Windows 和 Mac 仍是 1.2.3。Official iOS is at 1.27.0; Windows and Mac remain at 1.2.3.
- 在 Ubuntu 24.04（Docker 29.1.3、Compose 2.40.3）的独立测试实例上验收：从 1.6.0 带数据升级，真实模型用 Shell 和 Read 读到升级前存的记忆、Read `store.db` 被拒，备份后恢复成新实例，模拟的旧版 Docker / Compose 被拒绝。Accepted on an isolated Ubuntu 24.04 instance: an upgrade from 1.6.0 with data, a real model reading memory saved before the upgrade with Shell and Read while Read on `store.db` was refused, backup and recovery into a new instance, and simulated old Docker and Compose being refused.
